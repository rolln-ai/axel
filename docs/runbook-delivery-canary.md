# Production delivery canary

The delivery canary sends a synthetic event through the production ingest,
router, native queue, and Postgres destination. It does not use customer
webhooks or a customer destination.

For the initial merge only, the PR squash title or merge commit message must
contain `[skip render]`. Render git auto-deploy is still live until the first
protected Render workflow runs its hardener, so this guard prevents the merge
itself from racing the migration, provisioning, and staged proof below.

## Provision the isolated canary

Migration `0073_delivery_canary_receipts.sql` creates the controlled destination
table. Its checks accept only the four fields generated by
`scripts/delivery-canary.mjs` and reject payloads larger than 1 KiB. The table
stores no credentials, workspace identifiers, source identifiers, or customer
data.

Apply pending migrations with the standalone protected workflow and wait for
terminal success before running the provisioner:

```sh
gh workflow run migrate-postgres-run.yml --ref main \
  -f target=production -f confirm=apply
gh run list --workflow migrate-postgres-run.yml --branch main \
  --event workflow_dispatch --limit 5
gh run watch <migration-run-id> --exit-status
```

Replace the placeholder with the run ID printed by `gh run list`. Do not rely
on a deployment workflow's later migration step: migration `0073` must already
exist for the provisioner preflight.

After that run succeeds, use a trusted operator machine with an admin
`DATABASE_URL` that can manage roles and owns the Axel schema. The database
address must be reachable by the delivery runtime and must pass Axel's
destination SSRF policy. Never use a customer database or workspace for this
canary.

The provisioner requires four environment-only inputs:

- `DATABASE_URL`: the production control-plane admin DSN. It is used for the
  reconciliation session and is not stored as the destination credential.
- `CREDENTIALS_MASTER_KEY`: the existing 64-hex production key. Do not generate
  a new one for this command.
- `AXEL_CANARY_SOURCE_TOKEN`: a dedicated token matching
  `axt_[A-Za-z0-9_-]{32,128}`.
- `AXEL_CANARY_WRITER_PASSWORD`: a dedicated random password of 32 to 256
  bytes.

Enter the existing secrets without shell echo, generate the two new values
without putting plaintext in shell history, save the new values in the team's
password manager, and run the following block in Bash. macOS zsh gives `read`
flags different meanings, so start `bash` first rather than pasting this block
at a zsh prompt.

```bash
set -euo pipefail
read -rsp 'Production DATABASE_URL: ' DATABASE_URL; printf '\n'
read -rsp 'Production CREDENTIALS_MASTER_KEY: ' CREDENTIALS_MASTER_KEY; printf '\n'
export DATABASE_URL CREDENTIALS_MASTER_KEY

export AXEL_CANARY_SOURCE_TOKEN="axt_$(openssl rand -hex 32)"
export AXEL_CANARY_WRITER_PASSWORD="$(openssl rand -hex 32)"

pnpm --filter @axel/shared build
node scripts/provision-delivery-canary.mjs

unset DATABASE_URL CREDENTIALS_MASTER_KEY AXEL_CANARY_WRITER_PASSWORD
export -n AXEL_CANARY_SOURCE_TOKEN
```

Do not paste any of these values into command arguments, a URL, an issue, or a
log. The provisioner does not load dotenv files, accept command-line values, or
print database responses. The block clears the admin DSN, master key, and
writer password immediately, then removes the source token's export attribute
so later child processes receive it only through explicit standard input. Keep
the same source token for routine reruns. A deliberate token rotation can take
up to five minutes to replace an ingest-edge cache entry.

The operation is advisory-locked and idempotent. It reserves these fixed
identities:

| Resource | Fixed identity |
| --- | --- |
| Workspace | `ws_delivery_canary` |
| Source | `src_delivery_canary` |
| Route | `route_delivery_canary` |
| Postgres destination | `dst_delivery_canary_postgres` |
| Destination credential | `cred_delivery_canary_postgres` |
| Database role | `axel_delivery_canary_writer` |

An existing fixed ID with a different owner, name, type, or relationship causes
the operation to roll back. The canary workspace must have no members or extra
sources, routes, destinations, or route bindings. The reconciled workspace is
billing-exempt, keeps raw data for one day as a fallback, and keeps canary dead
letters and replay requests for seven days. Its source is transient with a
zero-day raw override, a small body limit, and a dedicated SHA-256 token hash.

The provisioner derives a writer DSN from `DATABASE_URL` but removes the admin
identity and role-switch parameters. It encrypts that DSN with Axel's shared
AES-256-GCM v2 implementation and binds it to the canary workspace and
destination using the canonical AAD helper. Plaintext is never written to a
control-plane column.

The role is reconciled to `LOGIN`, `NOINHERIT`, `NOSUPERUSER`, `NOCREATEDB`,
`NOCREATEROLE`, `NOREPLICATION`, and `NOBYPASSRLS`, with no role memberships or
owned database objects. Its explicit grants are equivalent to:

```sql
GRANT CONNECT ON DATABASE your_database_name TO axel_delivery_canary_writer;
GRANT USAGE ON SCHEMA public TO axel_delivery_canary_writer;
GRANT INSERT (payload) ON public.delivery_canary_receipts
  TO axel_delivery_canary_writer;
```

The script removes the role's other direct database, schema, table, sequence,
and function grants before applying those privileges. It verifies that the role
has no direct database ACL outside the target database, no effective access to
any other non-system relation in the target database, and no effective execute
privilege on a non-system `SECURITY DEFINER` function. This last check matters
because a direct function `REVOKE` cannot override an execute grant inherited
from `PUBLIC`.

Postgres has no per-role deny that cancels a cluster-wide `PUBLIC CONNECT`
grant. The canary role and DSN are scoped to the target database; if the same
cluster hosts other application databases, its cluster baseline must revoke
unwanted `PUBLIC CONNECT` grants or the canary must use a dedicated cluster.

The provisioner then logs in as the writer, inserts a valid canary payload
inside a transaction, proves that `SELECT`, `UPDATE`, and `DELETE` on the
receipt table fail, and proves that `SELECT` and `INSERT` on control-plane
tables fail. The transaction is rolled back, so verification writes no receipt.
A role that owns database objects causes a fail-closed rollback instead of an
ownership rewrite.

The fixed route is active and declarative. Its binding is:

```json
{
  "table": "delivery_canary_receipts",
  "mode": "jsonb_blob",
  "payload_column": "payload"
}
```

After the provisioner succeeds, configure the same canary values in both the
GitHub `Monitoring` and `Production` environments. Every `AXEL_CANARY_*` input
is read through `secrets.*`, including URLs and header names. The writer
password, admin DSN, and master key do not belong in GitHub:

Create the `Monitoring` environment before setting its secrets. It must have no
required reviewers and no wait timer; a protected approval gate would leave the
15-minute unattended schedule queued instead of monitoring production.

```bash
set -euo pipefail
read -rsp 'Production DELIVERY_CANARY_RECEIPT_TOKEN: ' DELIVERY_CANARY_RECEIPT_TOKEN
printf '\n'
export -n DELIVERY_CANARY_RECEIPT_TOKEN

if [[ "$DELIVERY_CANARY_RECEIPT_TOKEN" == "$AXEL_CANARY_SOURCE_TOKEN" ]]; then
  echo 'The receipt token must differ from the ingest source token.' >&2
  exit 1
fi

read -rsp 'Vercel operator token: ' VERCEL_TOKEN; printf '\n'
read -rp 'Vercel dashboard project ID: ' VERCEL_PROJECT_ID_DASHBOARD
read -rp 'Vercel team scope ID or slug: ' VERCEL_SCOPE
export VERCEL_TOKEN

printf %s "$DELIVERY_CANARY_RECEIPT_TOKEN" \
  | npx --yes vercel@58.4.0 env add DELIVERY_CANARY_RECEIPT_TOKEN production \
      --sensitive --force \
      --project "$VERCEL_PROJECT_ID_DASHBOARD" \
      --scope "$VERCEL_SCOPE"

unset VERCEL_TOKEN VERCEL_PROJECT_ID_DASHBOARD VERCEL_SCOPE

for github_environment in Monitoring Production; do
  printf %s 'https://ingest.axelapp.ai/in/src_delivery_canary' \
    | gh secret set AXEL_CANARY_INGEST_URL --env "$github_environment"
  printf %s 'x-axel-token' \
    | gh secret set AXEL_CANARY_INGEST_AUTH_HEADER --env "$github_environment"
  printf %s "$AXEL_CANARY_SOURCE_TOKEN" \
    | gh secret set AXEL_CANARY_INGEST_AUTH_VALUE --env "$github_environment"
  printf %s 'https://app.axelapp.ai/api/ops/delivery-canary/receipt?probe={probe_id}' \
    | gh secret set AXEL_CANARY_RECEIPT_URL --env "$github_environment"
  printf %s 'x-axel-canary-token' \
    | gh secret set AXEL_CANARY_RECEIPT_AUTH_HEADER --env "$github_environment"
  printf %s "$DELIVERY_CANARY_RECEIPT_TOKEN" \
    | gh secret set AXEL_CANARY_RECEIPT_AUTH_VALUE --env "$github_environment"
done

unset AXEL_CANARY_SOURCE_TOKEN DELIVERY_CANARY_RECEIPT_TOKEN
```

The pinned Vercel command reads the receipt token from standard input, receives
CLI authentication through the environment rather than a process argument,
targets only the dashboard project and Production environment, marks the value
sensitive, and creates or replaces it without writing plaintext to disk. Never
fetch a production value into terminal output merely to compare it.

## Receipt endpoint

Set `DELIVERY_CANARY_RECEIPT_TOKEN` on the production dashboard to a random
value of at least 32 characters. The receipt request is:

```text
GET /api/ops/delivery-canary/receipt?probe={probe_id}
X-Axel-Canary-Token: <DELIVERY_CANARY_RECEIPT_TOKEN>
```

A successful response contains exactly `probe_id` and `received_at`. The route
does not return the stored payload. It sends `Cache-Control: no-store`, hides
authentication failures behind a 404 response, and prunes receipts older than
seven days after successful reads.

Keep all six `AXEL_CANARY_*` GitHub secrets identical between `Monitoring` and
`Production`. The ingest, receipt, and Vercel automation-bypass credentials
must all be distinct. Do not put either Axel token in a URL.

The Vercel deployment workflow proves the exact staged dashboard URL before it
promotes it. The GitHub `Production` environment or repository must contain the
dashboard automation-bypass value under the exact secret name
`VERCEL_AUTOMATION_BYPASS_SECRET_DASHBOARD`. The workflow injects that value as
`x-vercel-protection-bypass` while retaining the Axel receipt-auth header. Do
not create generic `AXEL_CANARY_RECEIPT_PROTECTION_BYPASS_*` GitHub secrets;
the workflow does not read them.

## First production rollout

After the standalone migration reaches terminal success, run the provisioner,
install the dashboard receipt token, and configure both GitHub environments.
Then dispatch these workflows strictly in order:

```sh
gh workflow run deploy-vercel.yml --ref main \
  -f reason='First delivery-canary rollout'
gh run list --workflow deploy-vercel.yml --branch main --event workflow_dispatch --limit 5
gh run watch <vercel-run-id> --exit-status

gh workflow run sync-render-secrets.yml --ref main -f service=all
gh run list --workflow sync-render-secrets.yml --branch main \
  --event workflow_dispatch --limit 5
gh run watch <render-secret-sync-run-id> --exit-status

gh workflow run deploy-render.yml --ref main \
  -f reason='First delivery-canary rollout' -f service=all
gh run list --workflow deploy-render.yml --branch main --event workflow_dispatch --limit 5
gh run watch <render-run-id> --exit-status

gh workflow run deploy-cloudflare.yml --ref main \
  -f reason='First delivery-canary rollout' -f service=all
gh run list --workflow deploy-cloudflare.yml --branch main --event workflow_dispatch --limit 5
gh run watch <cloudflare-run-id> --exit-status
```

Replace each placeholder with the run ID printed by the immediately preceding
`gh run list`. Do not sync Render secrets until Vercel reaches terminal
success, do not deploy Render until the save-only secret sync succeeds, and do
not dispatch Cloudflare until Render reaches terminal success. The sync is
required on the first rollout because it installs the previously absent
`sync:false` values on `axel-delivery-workers`; it does not deploy a service.
All four workflows share the `production-deploy` concurrency group. GitHub
retains only one pending run in a concurrency group, so dispatch and wait for
each operation one at a time. Stop on any non-success result and investigate
before continuing.

## Start the 72-hour observation window

The `Monitoring` environment must be able to resolve `SENTRY_DSN`. Prefer an
environment secret; an existing repository secret of the same name is also
available as a fallback. A missing DSN does not fail the canary—the Sentry
steps skip—so confirm this separately instead of inferring it from a green run.

After the complete rollout sequence succeeds, dispatch the first canary and
wait for terminal success:

```sh
gh workflow run delivery-canary.yml --ref main
gh run list --workflow delivery-canary.yml --branch main \
  --event workflow_dispatch --limit 5
gh run watch <canary-run-id> --exit-status
```

In Sentry, verify that the `production-delivery-canary` cron monitor now
exists, the manual run recorded a successful check-in, and its missed/error
check-in alert reaches the intended on-call route. The monitor should show a
15-minute schedule, a five-minute maximum runtime, and a 30-minute check-in
margin. Keep both the GitHub scheduled workflow and the Sentry monitor under
observation for the full 72 hours.

If Sentry monitor creation or alert delivery cannot be proved before the
window starts, assign a named on-call owner to monitor the Production Delivery
Canary runs in GitHub Actions for failures and missing scheduled runs throughout
the 72 hours. Sentry remains the target state; Actions-only monitoring is an
explicit temporary fallback, not silent acceptance of missing alerts.
